# Changelog

## 2.252

- Upgrading from upstream version 2.251 -> 2.252

> Upstream v2.252: https://github.com/NeySlim/ultimate-ca-manager/releases/tag/v2.252
>
> ## What's Changed
>
> ### Added
> - LDAP: a StartTLS option switches a plain LDAP connection to TLS before the service and user binds, with the existing certificate verification; it was documented but never sent, so passwords crossed in clear (RFC 4513 §3, migration 137).
> - SAML: the Single Logout endpoint announced in the SP metadata ignored LogoutRequests. A LogoutRequest signed by the IdP, naming its Destination, issued within the clock window and not seen before, now closes the session of its NameID in that browser and gets a LogoutResponse signed with the SP RSA key, unsigned with a warning when the SP key is not RSA (SAML Profiles §4.4).
> - Deployment: a deploy target can be an HTTP API instead of an SSH host, with a URL, a method, encrypted request headers and a body template rendered from the certificate (`{{cert_pem|json}}`, `{{fullchain_pem}}`, `{{cn}}`, `{{serial}}`...), through the same delivery queue; the private key is sent only with an explicit opt-in over verified HTTPS, with an optional pasted trust anchor for a self-signed appliance (discussion #428, requested by @gjarassier, migration 131).
> - EST: the encrypted `serverkeygen` key can now go to an EC client certificate by key agreement (ephemeral-static ECDH, RFC 5753), and the key transport or key agreement and the content cipher follow the CSR's SMIMECapabilities in the client's order of preference, with AES-CBC when no listed content cipher is available. A list naming only key transport or agreement algorithms UCM lacks is refused with the supported ones named, as is an RSA client key under 2048 bits (RFC 7030 section 4.4.2).
> - EST: with the `allow_empty_username` setting of `PATCH /api/v2/est/config`, Basic authentication accepts an empty username and the password alone (RFC 7030 §3.2.3).
> - SCEP: a "Serve on plain HTTP" setting, off by default, also answers SCEP on the HTTP protocol port (8080 by default) for clients such as sscep that cannot use HTTPS; RFC 8894 §7.10 needs no TLS, as the CMS envelope protects the messages.
> ### Changed
> - AD Connector: saving a base DN without DC components, which names no domain, is refused with 400; saving or testing a Global Catalog port (3268, 3269) or a server written with a port or an `ldap://` scheme is refused too, and a Kerberos realm must match the base DN's in capitals exactly (RFC 4120 §6.1).
> - SSO providers: an unknown `default_role` is refused instead of being stored as viewer, and an empty one, "None" in the form, gives no implicit role; an existing provider whose default role is empty or unknown keeps viewer (migration 137).
> - LDAP: a new provider without SSL/TLS uses StartTLS by default, so passwords do not cross in clear (RFC 4513 §6.3.3); existing providers keep their setting.
> - ACME server: revokeCert refused an account other than the one that ordered the certificate even when it held valid authorizations for all its identifiers. Such an account may now revoke a certificate this ACME server issued, as RFC 8555 §7.6 requires; an authorization granted by auto-approval does not count.
> - ACME server: the `notBefore` and `notAfter` of a newOrder were echoed, then ignored, so the certificate got the profile's 90 days. They are now issued exactly: a window longer than the profile allows, outside the issuing CA's, already past or unreadable is refused as `malformed`, one a policy forbids as `badCSR` at finalize (RFC 8555 §7.4).
> - WSTEP: a certificate issued under a template carries that template's EKUs instead of the ones the request asks for, as on renewal and in AD CS.
> - WSTEP: a request without Key Usage gets the one its template configures, else the one of its template's kind, at issuance and renewal: digitalSignature, keyEncipherment and nonRepudiation for an emailProtection or EFS template, digitalSignature and keyEncipherment for Smartcard Logon, digitalSignature alone for clientAuth, instead of the server pair for all.
> - XCEP: the Username/Password policy endpoint announces a client-supplied subject for every template, machine templates included, since that binding carries no directory identity to build one from.
> - PostgreSQL: UCM connects with psycopg 3, which sends values apart from the statement, so a database error that quotes the statement no longer carries them. psycopg2 is no longer shipped, and a `postgresql+psycopg2://` URL now uses psycopg 3.
> - Dependencies: SQLAlchemy 2.1 is accepted, now that every PostgreSQL URL reaches psycopg 3.
> - EST, SCEP and TSA share one CMS SignedData builder; no wire change.
> - EST: `/csrattrs` lists keyUsage, subjectAltName and extKeyUsage as bare OIDs instead of inside an extensionRequest, a form RFC 9908 §5.2 declares incorrect; the `csrattrs_legacy_encoding` setting of `PATCH /api/v2/est/config` restores the former shape.
> - EST: enrollment refusals are sent as `text/plain` with the reason, such as a body that is not base64 or not a PKCS#10 CSR, a CA name constraint or the rate limit, instead of an HTML page saying "Enrollment failed" or JSON (RFC 8951 §5).
> - EST: `simplereenroll` without a client certificate answers 403 instead of a 401 offering Basic authentication, which that route refuses (RFC 7030 §3.2.3), and `/fullcmc` answers 501 instead of 405 (RFC 7030 §3.2.2).
> - EST: a CSR whose `challengePassword` is not the `tls-unique` value of its TLS 1.2 connection to UCM, or that arrives over TLS 1.3 or through a proxy where none can be checked, is refused with 400 on `simpleenroll`, `simplereenroll` and `serverkeygen` instead of being certified unchecked (RFC 7030 §3.5).
> - SCEP: a RenewalReq signed by a certificate issued through the same endpoint is authenticated by that certificate, so its challenge password is no longer compared and a rotated secret no longer blocks renewal; a certificate from another profile or protocol still needs the endpoint's challenge.
> - SCEP: every FAILURE reply now carries a failInfoText attribute giving the reason (RFC 8894 §3.2.1.4).
> - ACME proxy: the directory no longer advertises `keyChange`, which the proxy refuses, and a challenge none of the requesting account's orders lists is now answered 404 instead of 403.
> - ACME proxy: a client's `profile`, `notBefore` and `notAfter` are now passed to the upstream CA, so a CA that does not accept them refuses the order with its own error instead of silently applying its defaults.
> - SSH: certificates are valid from 5 minutes before issuance, so a server whose clock lags accepts them at once, and the KRL version now grows with each generation instead of staying 0 (PROTOCOL.krl).
> - mTLS: the trusted CA is now the only trust anchor of the HTTPS port. A client certificate from its parent or from a sibling intermediate passed the TLS handshake, and with it EST enrollment; it is now refused (RFC 5280 §6.1).
> - Dashboard: the Recent Activity feed shows the whole audit trail only with `read:audit`, as the Audit Logs page does; without it, a user sees their own events.
> - TOTP: the account actions that ask for a code (confirm, disable, regenerate recovery codes) accept one time step of clock drift either way, as the login does.
> - Access Control: the API no longer lets a custom role inherit from a built-in role, which the page never offered; a role that already does keeps its parent.
> - TSA: a request carrying any extension, critical or not, is now refused with unacceptedExtension, and a malformed one, trailing bytes included, with badDataFormat instead of systemFailure (RFC 3161 §2.4.1).
> - TSA: tokens carry genTime in whole seconds with a declared accuracy of one second, and `/tsa` matches `application/timestamp-query` or `application/octet-stream` exactly, ignoring case, instead of any type containing `timestamp-query`.
> - CRL: with delta CRLs enabled, each complete CRL is now followed by a delta on it, so the shared CRL number advances by two per regeneration.
> - Approvals: a revocation request approved while its certificate is on hold now revokes it for good with the requested reason, instead of waiting for the hold to be lifted.
> - Sign CSR, EST, SCEP, WSTEP and ACME: a subject beyond the RFC 5280 bounds (CN over 64 characters, a country that is not two letters in a PrintableString) was signed as received; it is now refused with the reason, as on the issue form. An EST, SCEP, WSTEP or in-place renewal that keeps its certificate's subject is not affected; an ACME renewal is.
> - Sign CSR (single, bulk and approval): a request without Key Usage signed as client, code signing or S/MIME got none, so the key was unrestricted; it now gets its type's Key Usage, as on the issue form.
> - Certificates: on the issue form, Sign CSR, EST and WSTEP, a valid emailAddress in the subject is now also an rfc822Name in the SAN for every certificate type, not only email and combined (RFC 5280 §4.1.2.6); SCEP keeps the request's SAN as sent.
> - Certificates and ACME: a DNS name holding an underscore (`my_host.example`, `_sip._tcp.example.com`, also as the CN of a server or device certificate without SAN whose template allows DNS names) or in IP-address form is now refused, as RFC 5280 §4.2.1.6 requires. An EST, SCEP, WSTEP or in-place renewal keeps the names its certificate already carries; an ACME order does not.
> - EST, WSTEP and SCEP: every certificate was recorded as a server certificate, so an S/MIME or client one showed as "Server" in its details and in the API of a renewal approval request. Each now records the type it is signed as (EST: device; SCEP and WSTEP: from its EKUs, by one rule); certificates issued earlier keep their recorded type.
> ### Fixed
> - Account: a wrong current password on the password change form answered 401, which logged the user out; it now answers 403 and the form shows the error.
> - AD Connector: an LDAP search that the domain controller answered with an error (busy, unavailable, time limit, a base DN it does not hold, missing read rights) read as "account not found", so WSTEP refused the requester with 400. It now counts as a directory failure, answered 500 like an unreachable DC.
> - mTLS: a static file request sent without the session cookie, as browsers fetch the favicon, opened a new certificate session and wrote a `login_success` audit event, several per page refresh. Static files no longer open a session, so a page load logs in once.
> - mTLS: once a session expired, opened by password or by certificate, each of the parallel calls still carrying its cookie logged in again with the client certificate, opening one session and one `login_success` event per call. They now share a single new session, and the web interface redirects to the login page once for a burst of 401 answers.
> - ACME proxy: every upstream CA error reached the client as a 500 `serverInternal`, so a rate limit, a refused name or a refused CSR looked like a proxy failure. The upstream type, status, subproblems and Retry-After now reach the client, revocation included (RFC 8555 §6.6, §6.7).
> - ACME proxy: when the DNS provider refused the TXT record, the challenge was still submitted and failed on the shared upstream account. The order now turns invalid without any upstream request, its other challenges are not submitted either, a retried order on the same authorizations is validated, and the TXT records of invalid or deactivated orders are removed.
> - ACME proxy: an upstream error on a certificate download reached the client as a 200 carrying the error body. It is now relayed as an ACME problem with its status.
> - ACME proxy: when the upstream CA refused or did not take the challenge response, the order stayed pending with its TXT records published and no later order could validate the name. The order now turns invalid for good with the upstream error, its records are removed, a retried order is validated, and a refused nonce is retried up to three times by the proxy and the ACME client (RFC 8555 §6.5, §7.1.6).
> - ACME proxy: a CSR that did not name exactly the order's identifiers reached the client as a 500 `serverInternal` when the upstream CA refused it as `unauthorized`. It is now refused with `badCSR` before reaching the upstream CA (RFC 8555 §7.4).
> - ACME server and proxy: proxy responses other than newNonce and revocation carried no `Link: rel="index"`, and a successful revocation answered with an empty `text/html` body. Every proxy response but the directory now links it, and a revocation answers 200 with no body and no media type (RFC 8555 §7.1, §7.6).
> - ACME proxy: the directory listed the upstream profiles but `profile` and `notAfter` were never passed upstream, so a client got the default profile and validity. Both are now passed, a retried request reuses a pending order only if it carries the requested dates and the same `replaces`, and a profile the upstream CA does not offer is refused with `invalidProfile`.
> - ACME proxy: the challenge was read upstream with a POST-as-GET before the TXT record was published, which starts the validation on some CAs. It is now read through its authorization (RFC 8555 §7.5.1, erratum 5729).
> - ACME proxy: the upstream Retry-After of an order, authorization or finalization was dropped, and upstream requests carried the HTTP library's User-Agent. Both are now relayed and set (RFC 8555 §6.1, §7.1.3).
> - RFC 2136 DNS provider: a server given by host name always failed with an empty message, and a filled-in zone was overridden by the zone the system resolver saw. The name is now resolved and each of its addresses tried, the configured zone is used for the names inside it, and otherwise the zone is read from the configured server's SOA.
> - ACME client: with ARI, a certificate renewed at the very start of the suggested window, an expired certificate was still checked and any Retry-After was taken as is. It now renews at a random moment drawn once inside the window, skips expired certificates and keeps the checking interval between one minute and one day (RFC 9773 §4.2, §4.3).
> - ACME client: an HTML error page from the CA was reported as a JSON parse error, an RSA account key with an exponent other than 65537 got a padded JWK exponent, and an unquoted `rel=alternate` link was ignored. The status and Retry-After are now reported, the exponent is minimal (RFC 7518 §6.3.1.2) and every RFC 8288 form is read.
> - DNS providers: Cloudflare, OVH, Bunny, DNS Made Easy, IONOS, NS1, Rackspace, Scaleway, Tencent Cloud, Dynu, Porkbun, Netcup, ClouDNS and INWX followed redirects with their credentials, and a Cloudflare delete the API refused was reported as a success. Redirects are no longer followed and the refusal is reported.
> - Approval e-mails: without a Base URL or server FQDN, the link to the request followed the Host header the requester sent; the e-mail now goes without a link.
> - Password reset: the e-mailed link pointed at `https://localhost:8443`. It now uses the Base URL, else the server FQDN, never the request's Host; when neither is set, Forgot password is hidden and the reset is refused with a warning in the log.
> - OIDC: an ID token whose `azp` named another client was accepted when it had a single audience; it is now refused (OpenID Connect Core §3.1.3.7).
> - LDAP: a second factor the user had enrolled, even one Enforce 2FA required, was never asked at sign-in. LDAP sign-ins now ask for it, as local ones do.
> - Certificates: a DNS name with a space, a trailing dot, a wildcard past the first label, a lone `*`, an all-digit last label or an `xn--` label that is no A-label was issued by the form, the API, Sign CSR, EST and SCEP. Such names are now refused with the reason, a 400 or a SCEP failure naming them (RFC 5280 §4.2.1.6), and an internationalized name is issued as its A-label instead of answering 500 (RFC 9549).
> - Sign CSR, EST and WSTEP: a request without SAN got its CN as a DNS name whatever it held (`DNS:John Doe`, and on a sub-CA too), and a non-ASCII CN answered 500. Only a CN in DNS name syntax now gives one, a single label only on a server or device certificate and never on S/MIME or a sub-CA, with a notice when a host-like server CN gives none.
> - WSTEP: a template without serverAuth signed its certificates as server ones, so a user CN (`jdoe`) became `DNS:jdoe`. A template with emailProtection or EFS now issues S/MIME certificates, one with clientAuth or Smartcard Logon (VPN Client included) client ones and one with code signing alone code-signing ones, which take no DNS name from a one-label CN.
> - Sign CSR: a refusal for a parent CA with pathLen 0, a name outside the CA name constraints or an unacceptable key answered 500 "Failed to sign CSR". It now answers 400 with the reason; an empty subject takes as CN the first SAN name that fits in 64 characters.
> - CAs: the error for a DNS name constraint with a leading dot suggested `.example.com`, the form it refuses.
> - Rate limiting: a 429 from a login route's own limit carried the general limit in `X-RateLimit-Limit` (30 instead of 5) and no `Retry-After`. It now names the limit that refused the request and when to retry.
> - ACME server: a body that was not JSON, a payload that was not an object or an unreadable date answered 500 `serverInternal`. They now answer 400 `malformed` (RFC 8555 §6.2, §7).
> - ACME server: a missing nonce answered `malformed` and a nonce outside base64url `badNonce`, the reverse of RFC 8555 §6.5; HEAD on newNonce answered 204 without a link to the directory. Both errors now carry the right type, and newNonce, on the server and the ACME proxy, answers 200 to HEAD and 204 to GET with `Link: rel="index"` (§7.2).
> - ACME server: every response stored a nonce that was never deleted, so the nonce table only grew. The 6-hourly ACME purge now also deletes expired and consumed nonces.
> - ACME server: a CSR whose common name is one of the order's IP addresses, as lego v4 and the UCM ACME client send for an IP order, was refused as `badCSR`. Such a CN is now matched against the IP identifiers (RFC 8738).
> - ACME server: the directory advertised the public host as `caaIdentities` even when CAA identifiers were configured, while finalize checked CAA against the configured ones. Both now use the same list (RFC 8555 §7.1.1).
> - ACME server: an order past its expiry, or one whose valid authorization had expired, could still be finalized. Finalize now answers 403 `orderNotReady` and the order becomes invalid, and an expired valid authorization reads `expired` (RFC 8555 §7.1.6, §7.4).
> - ACME server: an account created with External Account Binding was returned without its `externalAccountBinding` field. The new account object, on the server and the ACME proxy, now carries it with the value of the request (RFC 8555 §7.3.4).
> - ACME server: a POST-as-GET on a challenge started its validation, so a client reading the challenge before preparing its response, the ACME proxy included, lost the order. An empty payload now only reads the challenge, and only a response object such as `{}` starts the validation (RFC 8555 §6.3, §7.5.1).
> - ACME server: an order accepted with `replaces` did not show it in the order object, and the finalize response lacked the profile. Every order object (newOrder, read, finalize) now carries `replaces`, `profile` and the requested dates (RFC 9773 §5).
> - ACME server: tls-alpn-01 accepted a validation certificate whatever its subjectAltName. The SAN must now hold exactly the identifier being validated, one dNSName or one iPAddress (RFC 8737 §3, RFC 8738 §6).
> - WSTEP: a request with no `wst:RequestType` or another one than Issue was served as an issuance, a message whose `wsu:Timestamp` had expired was accepted, and the fault for an unreadable request did not relate to its message. Such requests now get a SOAP fault (`wsse:MessageExpired` past a 5 minute skew), which carries `RelatesTo`.
> - WSTEP: a PKCS#10 request sent under the `#PKCS7` ValueType, as in the MS-WSTEP example, was refused as a malformed CMS envelope. The request format is now read from its content, whatever the ValueType says.
> - WSTEP: a plain PKCS#10 request got no CMC Full PKI Response in its answer, which MS-WSTEP requires for every request, and the one a CMC request got carried its status under a wrong OID. Every request now gets one, with CMCStatusInfoV2 under `id-cmc-statusInfoV2` (RFC 5272 §6.1.1).
> - WSTEP: the template a request named (szOID_CERTIFICATE_TEMPLATE by OID, szOID_ENROLL_CERTTYPE by name) was ignored and the template chosen by EKU, so of two templates with the same EKUs the oldest always won, and a template the CA does not offer was issued anyway. The named template is now issued, an unknown, inactive or conflicting one is refused, and a request naming none is still matched by its EKUs.
> - XCEP: the policy announced no certificate template extension, so Windows CertEnroll named no template in its request and of two templates with the same EKUs the oldest was issued. Each template now announces its `szOID_CERTIFICATE_TEMPLATE` extension, which Windows copies into the request, and its revision is the one the issued certificate carries.
> - WSTEP and XCEP: a fault caused by the request (unknown template, EKUs the template does not issue, failed authentication, malformed message) carried the `s:Receiver` code, and a failure on the CA side (signing error, unreachable directory, no template configured to issue under) went out as HTTP 400. Faults now follow SOAP 1.2: `s:Sender` with HTTP 400 for the request's (a Kerberos requester missing from Active Directory included), `s:Receiver` with HTTP 500 for the server's.
> - WSTEP: a request without Extended Key Usage, such as `openssl req -new` with a CN alone, was issued under the built-in OCSP Signing template, and one asking for OCSP Signing got serverAuth instead. A template whose EKUs are all never issued to an enrollee is now left out of the XCEP policy, and a request or renewal under it is refused.
> - WSTEP: an AD Connector enabled without a server or base DN answered a Kerberos request with HTTP 400 "The requester was not found in the directory". It now answers `s:Receiver` with HTTP 500, and an account whose objectSid is missing or malformed gets its own reason.
> - WSTEP: with XCEP and WSTEP set to two different CAs, the certificate carried a template OID derived from the WSTEP CA rather than the one XCEP announced, so Windows autoenrollment did not recognize it and enrolled again at every pulse. The certificate now carries the OID XCEP announced and still renews under its template once the XCEP CA setting changes; an OID derived by another UCM instance names no template.
> - Access Control: the built-in roles showed the permissions seeded at installation (12 for Operator, which is granted 41) and Administrator's `*` as ignored. They now show what UCM applies to them.
> - ACME DNS-01 on DuckDNS, Hurricane Electric and FreeDNS: these providers hold one TXT value per name, so the cleanup of one order cleared the value another order was still validating. The name is now left alone while another order in progress uses it.
> - ACME DNS-01 on DuckDNS, Hurricane Electric and FreeDNS: an order for a domain and its wildcard could not hold both values and failed at validation, and the ACME proxy replaced the CA's value with its clients' own. Such an order, or on DuckDNS one naming two hosts under the same subdomain, is now refused at the request before the CA is asked, and the proxy publishes only the CA's value there.
> - ACME client: a CA refusal of `replaces` whose message merely contained "rateLimited" was taken for a rate limit and not retried. A rate limit is now recognised by its problem type or a 429 only (RFC 8555 §6.7).
> - WSTEP: a certificate issued or renewed under a template did not record it, so the template's usage count left it out, the template could be deleted while in use, and its policies did not apply. The matched template is now recorded at issuance, so its approval policies cover revocation and renewal and an in-place renewal applies its SAN types, policy OIDs and custom extensions; certificates issued before are left as they are.
> - EST: the encrypted `serverkeygen` key came in a SignedData of type `data`, signed by the generated key itself and without signed attributes. It now comes in an RFC 5958 key package (`id-ct-KP-aKeyPackage`) with content-type and message-digest attributes, signed by an `EST key generator` certificate that the issuing CA issues on first use, HSM CAs included (RFC 7030 section 4.4.2, RFC 5652 section 5.3).
> - EST: without a requested encryption key, `serverkeygen` returned a PKCS#8 encrypted with the Basic password, or a CMS over mTLS. The key now comes as unencrypted `application/pkcs8` under TLS, and a request naming a key UCM does not hold, or a client certificate that does not allow key transport, is refused (RFC 7030 section 4.4.1).

## 2.251

- Upgrading from upstream version 2.249-5 -> 2.251

> Upstream v2.251: https://github.com/NeySlim/ultimate-ca-manager/releases/tag/v2.251
>
> ## What's Changed
>
> ### Added
> - CAs: Ed25519 and Ed448 keys can be generated for a root, intermediate or external CA, and an EdDSA CA key imported with or after its certificate (`POST /cas/import`, certificate import with its key, `POST /cas/<id>/key`) is accepted instead of a 400 (#436, reported by @Faraphel).
> - Certificates: templates and the issue form can add custom X.509 extensions, each an OID, a critical flag and its DER value in hex, and the certificate and CA details list the extensions UCM has no section for, with their raw value (#437, requested by @Faraphel).
> ### Security
> - Database: on PostgreSQL, an error carried the values bound to its statement, private keys included, into the logs despite hidden parameters: in the quoted statement, in the refused row of a NOT NULL or CHECK violation, and in the input a data error quotes. These are now removed from the message; its first line, the other DETAIL lines, HINT and SQLSTATE are kept.
> - Revocation: a key revoked as compromised was kept only for a certificate of a CA held here, so a Let's Encrypt certificate revoked as compromised then deleted let the ACME client certify the same key again. Such keys are now kept whatever CA issued the certificate, and refused at the request, the renewal and the finalization (migration 129).
> - Key recovery: a request named its certificate by number, and SQLite gives a deleted certificate's number to the next one created, so an approved request could export another certificate's private key, after a replacing restore in particular. Approval and recovery now answer 410 unless the number still names the certificate the request was opened on, and a replacing restore cancels the open requests on the certificates it removes.
> ### Fixed
> - XCEP: an ECDSA template was announced without its key algorithm, so Windows generated an RSA key of the curve's size and the enrolment failed. The template now names its curve (`ECDSA_P256`, `ECDSA_P384`, `ECDSA_P521`) as a signature key.
> - WSTEP: two templates sharing an EKU were told apart by their id alone, so a P-384 request was issued under the P-256 template and stamped with its OID. The request key must now fit the template: same curve or ML-DSA set, an RSA key at least as long.
> - WSTEP: the CMC envelope Windows signs with an ECDSA key was refused, because CertEnroll names the key type (`id-ecPublicKey`) as its signature algorithm. It is now verified with the digest the envelope declares.
> - Database: on PostgreSQL in a schema other than `public`, the integrity check reported 0 tables. It now counts the tables of the schema in use.
> - Database migration: to PostgreSQL in a schema other than `public` (a `search_path` in the URL), the sequences of the copied tables were never found, so the migration was refused at its verification. The sequences of the schema in use are now realigned, and the reset the failure message asks for names that schema.
> - Database: on PostgreSQL, the database reset waited forever for the transaction of its own request. It now closes that transaction before dropping the tables.
> - Renewals: a renewed OCSP responder certificate was signed with the policies' default digest instead of the original's, and a renewal that changed the digest said nothing. Both keep the original's while it is at least the CA key's and the policies allow it, else follow the issuance rule, and log the change (#397).
> - XCEP: an ECDSA template outside FIPS mode announced no request hash, and a P-384 or P-521 template asked for its template digest, SHA-256 by default. ECDSA templates are now schema 3 and announce the stronger of the template digest and the one matching their key; RSA templates outside FIPS mode stay schema 2, whose hash MS-XCEP requires to be nil (#397).
> - EST and mTLS: server-generated keys were always RSA-2048, so a policy refusing it (CNSA, strict FIPS profile) refused EST `serverkeygen` and user mTLS certificates. The key now takes the issuing CA's strength, in the family of the `serverkeygen` request's key when RSA or EC, else the CA's (a browser-usable type for mTLS), and moves to the closest type the policies allow (#397).
> - Issuance: EST, SCEP, WSTEP, Sign CSR, TSA signer and unconfigured ACME orders signed with SHA-256 whatever the CA key, and a P-384 CA's CRLs too. Every path now signs with the bound template's digest, raised to the one matching the CA key (SHA-384 for P-384, SHA-512 for P-521), as a preference that yields to the closest stronger digest the policies allow, or the strongest allowed (#397).
> - Docker: the images lacked pyspnego's Kerberos backend, which the DEB and RPM installs can add, so the Kerberos binding of Windows autoenrollment could not work in a container. Both images now ship it, at the pyspnego version the requirements resolve (#435, thanks @JPromi).
> - Restore: two DNS providers, ACME CA accounts or webhooks of the same name were merged into one row, and one credential was lost. A clashing row is now restored as `name (2)`, and the restore result lists it; an account is matched by its account URL and a webhook by its URL first.
> - DNS providers, ACME CA accounts and webhooks: the API accepted a name already in use. It now answers 409, on creation and on rename.
> - ACME client: a renewal imported its certificate into a new row, so the HTTPS binding, deployment bindings and webhooks stayed on the old one, which `revoke_on_renewal` then revoked. The certificate is now renewed in place, keeping its id, and `certificate.renewed` is emitted.
> - ACME client: the key of a finalization lived only in memory, so a restart or a failed import after the CA had issued lost the certificate. The key is now stored encrypted on the order before the request, and a status check, a finalization or the next renewal imports the certificate the CA already issued (migration 123).
> - ACME client: a manual and a scheduled renewal of one order could run at once and obtain two certificates. Each renewal or finalization now holds a lease on its order, which a stopped process leaves for 10 minutes: a second one gets a 409, and the scheduler skips the order.
> - ACME client: after 5 failed scheduled renewals an order was never renewed again, silently. It is now retried once a day, each failure emits the `acme_order.renewal_failed` webhook event, the order list shows the failure count and last error, and the scheduler task reports a warning.
> - ACME client: an order whose CA account had been deleted renewed under another account, possibly at another CA. The renewal and the order's other actions now stop with a message saying what to do, and deleting or deactivating an account is refused (409) while issued orders renew through it; each order's automatic renewal can now be turned off from the order list (`PATCH /api/v2/acme/client/orders/<id>`).
> - ACME client: a CSR whose key was revoked as compromised was refused only at finalization, after the CA had opened an order and checked the challenges at each renewal. It is now refused with a 409 by the request and before a renewal opens any order.
> - ACME client: a failed manual renewal answered a bare 500 and was neither counted nor audited. It now answers 409 or 422 with the reason, counts towards the order's failures and emits `acme_order.renewal_failed`.
> - ACME client: an order the CA answered 404 or 410 for was polled until the timeout, up to several minutes per scheduler pass. Polling now stops at once and the order turns invalid with the reason.
> - ACME client: a restart during the automatic validation left the order `processing` for good. Such an order now goes back to `pending` with a message, ready for Verify, within about 15 minutes of its last activity (at startup, then by a scheduler task every 15 minutes), so the orders another instance on the same database is validating are left alone.
> - ACME client and proxy: removing a DNS-01 TXT record deleted every value of its name, so cleaning up one order could erase the challenge of another order, or of the wildcard and apex sharing the name, still validating. DNS providers now remove only the value of that order; DuckDNS and Hurricane Electric, which hold one value per name, and FreeDNS, whose record list truncates TXT values, keep clearing the name and log a warning, and FreeDNS no longer removes the `_acme-challenge` record of another domain of the account.
> - DNS providers: Namecheap found no host in its API's answers, which carry an XML namespace, so publishing a TXT record replaced every record of the zone with it. The hosts and the mail setting (`EmailType`) are now read and written back, and nothing is written when the read fails.
> - ACME client: the order list loaded all its pages at once, so a rate limit answering 429 to one of them left the page empty. Pages now load four at a time, one answered 429 is retried after its `Retry-After`, and a page still missing leaves the orders obtained with a notice saying the list is partial.
> - FIPS mode: Smart Import and the converter accepted a file holding an Ed25519 or Ed448 key, which the other imports refuse, and every import let through an EdDSA X.509 certificate. They now answer the same FIPS refusal before parsing; an encrypted PKCS#8 key can only be refused once decrypted.
> - ACME client: the order list stopped at the 100 newest orders, so an older issued order disappeared from the page. The API now pages (`page`, `per_page`) and the page loads every order.
> - ACME client: the TXT records of a DNS-01 order whose automatic validation failed stayed in the zone. They are now removed once the order is invalid or its finalization failed; an order left pending keeps them for Verify.
> - ACME client: deleting a certificate after revoking it did not stop its order, and the next pass issued a new one. The order's automatic renewal is now turned off, with a message saying so.
> - ACME client: a renewal used a DNS provider that had been disabled, and an order reusing the key of a deleted certificate silently got a new key. Both now stop before the CA with a message.
> - ACME client: the help of the renewal threshold did not say that a certificate whose life is shorter than 1.5 times the threshold renews in its last third. It now does.
> - ACME client: with `revoke_on_renewal`, a revocation the CA refused or never received was only logged, and a certificate revoked here as compromised was revoked at the CA as superseded. The CA now gets the local reason when it is keyCompromise, affiliationChanged, superseded or cessationOfOperation and none otherwise, and a failed revocation is retried by the renewal task until the certificate expires, emitting `acme_order.revocation_failed`.
> - Revocation: a key revoked as compromised was forgotten once its certificate was deleted, so the ACME client could certify it again. The revocation record, written when the issuing CA is held here, now keeps the key's SHA-256 (migration 128).
> - Restore: a membership, deployment binding, CRL binding, template pin or role permission was matched by the source's row numbers first, and could overwrite another row here. Rows are now matched by what they name; an archive records the database it comes from, and its numbers count only there and only when they still name the same rows.
> - Restore: a replacing restore failed on PostgreSQL as soon as a CRL, a cached OCSP response, a session or an ACME client order pointed at a row it removed, and left such rows pointing at nothing on SQLite. Both engines now clear regenerable rows and queues, detach or drop history as deleting the row does, empty the optional links the schema does not enforce, and refuse any other link with the row named.
> - Restore: a replacing restore wrote the archive before removing what it does not carry, so a SCEP slug or a name still held by a removed row failed with a bare 500. Removals now come first, a homonym replacing the row here keeps its name unless a kept row still points at that row, in which case it is restored as `name (2)`, and a remaining database conflict names the table and the row.
> - Restore: an archive over 50 MB was refused with a 413 although it had been created without a word. The restore upload now accepts and reads up to `BACKUP_MAX_UPLOAD_MB` (512 by default), refusals name the setting, and creating an archive a restore would not read warns.
> - Restore: an archive older than 2.230 holding an API key or an ACME domain was refused whole, its nested group members went to whichever account held the source's number, and its nested WebAuthn keys were ignored. A row whose required link is a bare number, nested members included, is now left out and listed, and the WebAuthn keys come back.
> - Restore: a hybrid certificate pair came back with the source's number for its partner, which on another installation named another certificate or none. The partner, and a SCEP request's profile, are now found by name; for any link an older archive carries as a bare number, a row here keeps its own link unless the archive records none or the restore removes the target, and a new row is restored without it, with a warning in the result.

> - Backups: ACME client orders, approval requests and key recovery requests were in no archive, so a restore lost the renewal schedule and every pending request. They are now carried, an order with its pending key and its renewal link, and a recovery request follows its certificate's refid and is cancelled when that certificate is not there.
> - Restore: settings naming a row by its number (the SCEP and ACME issuing CAs, the ACME public TLS certificate and proxy account, OCSP responders, SCEP challenges, SCTs, cross-certificate URLs) kept the source's number, so SCEP or ACME could sign with another CA. > - Restore: a failed restore left on disk the certificate and plaintext key files of the authorities and certificates it had rolled back, and a replacement left those of the rows it removed. Files are now written, and those of removed rows deleted, only with the commit.
> - Restore: a client certificate was found again by its serial number, unique only per issuer, so the same certificate could come back twice and another one with that serial be overwritten. It is now found by its fingerprint, as the archive identifies it.
> - Restore: ACME accounts and EAB credentials came back dated from the restore, and webhooks without their authentication token. Both now come back as archived.

> - mTLS: a client certificate could not be enrolled, imported or assigned when an enrolled certificate of another CA had the same serial number, legitimate in X.509. An enrolment is now identified by its issuer and serial, at login and by a restore too (migration 130).
> - Backups: a webhook's authentication token was archived twice, in the clear and encrypted under the source's key, which no other installation can read. The archive now carries it in the clear only, and a restore ignores the encrypted copy of an older archive.
